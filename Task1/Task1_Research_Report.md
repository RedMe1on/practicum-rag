## Анализ контекста задачи

### Компания: QuantumForge Software
- **Тип**: Финско-эстонская продуктовая компания (SaaS + консалтинг)
- **Продукт**: Платформа «Цифровой двойник» для моделирования промышленных объектов
- **Клиенты**: ABB, Wärtsilä, скандинавские энергокомпании

### Статистика базы знаний
- ~18 000 Markdown/MDX файлов в репозиториях
- ~3 000 страниц Confluence (30 пространств)
- ~250 PDF-спецификаций (наследие)

- **Гибридный подход**: использовать локальные модели для конфиденциальных внутренних документов (архитектура, политики безопасности, данные клиентов)

- **Суверенитет данных**: необходимо соответствие GDPR (обработка данных в ЕС)

## 1. Сравнение LLM-моделей: локальные (Hugging Face) vs облачные (OpenAI / YandexGPT)

### 1.1 Качество ответов

| Критерий | Локальные (Hugging Face) | Облачные (OpenAI GPT-4o) | Облачные (YandexGPT) |
|----------|--------------------------|--------------------------|----------------------|
| Примеры моделей | Llama 3 70B, Mixtral 8x7B, Qwen 2.5 72B | GPT-4o, GPT-4o-mini | YandexGPT Pro |
| Качество ответов | Хорошее (7-8/10 для моделей 70B+). Сильно зависит от промпт-инжиниринга и файн-тюнинга | Отличное (9-10/10). Лучшее в классе рассуждение, следование инструкциям | Хорошее (7-8/10). Сильна в русском, достаточна в английском |
| Контекстное окно | 8K-128K токенов (зависит от модели) | 128K токенов | 32K токенов |
| Специализация | Требует файн-тюнинга для доменных задач | Сильные zero-shot, few-shot способности | Хороша для русскоязычных задач |

**Вывод для QuantumForge**: Для технической документации (преимущественно на английском) OpenAI GPT-4o обеспечивает превосходное качество. Локальные модели, такие как Llama 3 70B, жизнеспособны, но требуют больше усилий по промпт-инжинирингу.

### 1.2 Производительность (скорость)

| Критерий | Локальные (Hugging Face) | Облачные (OpenAI) | Облачные (YandexGPT) |
|----------|--------------------------|-------------------|----------------------|
| Задержка (на токен) | 20-50 мс (зависит от GPU) | 10-30 мс | 15-40 мс |
| Время до первого токена | 0,5-2 сек (холодный старт на локальном GPU) | 0,2-0,8 сек | 0,3-1 сек |
| Пропускная способность | 5-20 запросов/сек (один GPU) | 100+ запросов/сек | 50+ запросов/сек |
| Зависимость от железа | Требуется NVIDIA GPU (A100/V100) | Отсутствует | Отсутствует |

**Вывод для QuantumForge**: Облачные решения обеспечивают значительно лучшую пропускную способность и меньшую задержку. Локальное развёртывание требует выделенной GPU-инфраструктуры, что добавляет сложность.

## 2. Сравнение моделей эмбеддингов: локальные (Sentence-Transformers) vs облачные (OpenAI Embeddings)

### 2.1 Скорость создания индекса

| Критерий | Локальные (Sentence-Transformers) | Облачные (OpenAI text-embedding-3-large) |
|----------|-----------------------------------|------------------------------------------|
| Примеры моделей | all-MiniLM-L6-v2, all-mpnet-base-v2, E5-large-v2 | text-embedding-3-large, text-embedding-3-small |
| Скорость эмбеддинга | 1 000-5 000 док./сек (GPU) / 200-800 док./сек (CPU) | 500-2 000 док./сек (зависит от лимитов API) |
| Время на 21 250 документов | ~1-2 часа (GPU) / 5-10 часов (CPU) | ~3-6 часов (лимит ~3 000 запросов/мин) |
| Пакетная обработка | Эффективна (размер батча 32-256) | Ограничена лимитами API |

**Вывод**: Локальные модели могут быть быстрее при массовой индексации при наличии GPU. Облачные ограничены лимитами API, но не требуют инфраструктуры.

### 2.2 Качество поиска

| Критерий | Локальные (Sentence-Transformers) | Облачные (OpenAI) |
|----------|-----------------------------------|-------------------|
| Размерность эмбеддингов | 384 (MiniLM) / 768 (mpnet) / 1 024 (E5) | 3 072 (text-embedding-3-large) / 1 536 (small) |
| Балл MTEB | 63-69 (MiniLM/mpnet) / 70+ (E5-large) | 74+ (text-embedding-3-large) |
| Точность семантического поиска | Хорошая для технического текста (65-75% релевантности) | Отличная (80-90% релевантности) |
| Многоязычная поддержка | Требует специальных моделей | Встроенная (100+ языков) |
| Адаптация к домену | Можно файн-тюнить на доменных данных | Фиксированная (нельзя файн-тюнить) |

**Вывод для QuantumForge**:
- Эмбеддинги OpenAI обеспечивают превосходное качество «из коробки»
- Sentence-Transformers (E5-large-v2) — сильная локальная альтернатива
- Для технической документации на английском разница меньше, чем для общего текста

### 2.3 Стоимость владения и использования

#### Локальные (Sentence-Transformers)
| Статья расходов | Стоимость |
|-----------------|-----------|
| Инфраструктура | Включена в GPU-сервер LLM (совместное использование) |
| Хранение модели | ~1-2 ГБ (незначительно) |
| Инженерное время | ~4-8 часов на настройку |
| **Итого** | **~$0-50/мес** (предельная стоимость на существующем GPU) |

#### Облачные (OpenAI Embeddings)
| Статья расходов | Стоимость |
|-----------------|-----------|
| text-embedding-3-large | $0,13 / 1 млн токенов |
| Первоначальная индексация (21 250 док., ~500 токенов в среднем) | ~$1,40 (однократно) |
| Ежемесячные обновления (400 док.) | ~$0,03/мес |
| Эмбеддинги запросов (1 000 запросов/мес) | ~$0,05/мес |
| **Итого** | **~$2-5/мес** (очень дёшево для данного случая) |

**Вывод**: Стоимость эмбеддингов пренебрежимо мала для обоих вариантов. Облачные крайне дёшевы; локальные практически бесплатны при существующей GPU-инфраструктуре.

### **Итоговая рекомендация по эмбеддингам для QuantumForge**

| Сценарий | Рекомендация |
|----------|--------------|
| **Быстрый старт / простота** | **OpenAI text-embedding-3-small** (дёшево, хорошее качество) |
| **Максимальное качество** | **OpenAI text-embedding-3-large** |
| **Конфиденциальность / локальная обработка** | **Sentence-Transformers E5-large-v2** (лучшее локальное качество) |
| **Оптимизация по стоимости** | Любой вариант (оба очень дёшевы для эмбеддингов) |

## 3. Сравнение векторных баз данных: ChromaDB vs FAISS

### 3.1 Скорость поиска и индексации

| Критерий | ChromaDB | FAISS |
|----------|----------|-------|
| Индексация (10 тыс. векторов, 768 dim) | ~2-5 секунд | ~0,5-2 секунды |
| Индексация (100 тыс. векторов, 768 dim) | ~15-30 секунд | ~3-8 секунд |
| Задержка поиска (1 тыс. векторов) | ~1-5 мс | ~0,1-1 мс |
| Задержка поиска (1 млн векторов) | ~10-50 мс | ~1-5 мс (с IVF-индексом) |
| Алгоритм индексации | HNSW (по умолчанию) / brute force | IVF, HNSW, PQ, Flat (настраивается) |
| Масштабирование | Хорошо до ~10 млн векторов | Отлично (100 млн+ векторов) |

**Вывод**: FAISS значительно быстрее как при индексации, так и при поиске, особенно на масштабе. ChromaDB достаточен для малых и средних датасетов.

### 3.2 Сложность внедрения и поддержки

| Критерий | ChromaDB | FAISS |
|----------|----------|-------|
| Сложность настройки | Очень низкая (pip install, работает из коробки) | Средняя (требует знаний о конфигурации индексов) |
| Простота API | Простой Python API, доступен REST API | Более низкоуровневый C++/Python API |
| Персистентность | Автоматическая (SQLite + локальные файлы) | Ручная (сохранение/загрузка файлов индекса) |
| Фильтрация по метаданным | Встроенная (where-клаузы) | Требуется ручная реализация |
| Серверный режим | Chroma Server доступен | Требуется кастомная обёртка (напр., FastAPI) |
| Развёртывание в Kubernetes | Простое (stateless или persistent volume) | Требует кастомного развёртывания |
| Кривая обучения | 1-2 часа | 1-2 дня (типы индексов, параметры) |

**Вывод для QuantumForge**:
- **ChromaDB** намного проще в реализации и поддержке, особенно для команд без глубокого опыта в ML-инфраструктуре
- **FAISS** требует больше инженерных усилий, но даёт тонкий контроль

### 3.3 Удобство в работе

| Критерий | ChromaDB | FAISS |
|----------|----------|-------|
| Управление коллекциями | Встроенное (создание, удаление, список) | Ручное |
| Поддержка метаданных | Нативная (хранение + фильтрация по метаданным) | Требует отдельного хранилища |
| Хранение документов | Может хранить документы + метаданные + эмбеддинги | Только эмбеддинги (документы хранятся отдельно) |
| Бэкап/восстановление | Простой (копирование файлов / дамп SQLite) | Ручной (сохранение индекса + синхронизация метаданных) |
| Интеграция с экосистемой | Нативная поддержка LangChain, LlamaIndex | Поддержка LangChain, LlamaIndex |
| Отладка | Встроенные инструменты инспекции | Требует кастомных инструментов |

**Вывод для QuantumForge**: ChromaDB предоставляет более полноценный опыт «базы данных» со встроенным хранением документов и метаданных. FAISS — это лишь библиотека индексации.

### 3.4 Стоимость владения

| Критерий | ChromaDB | FAISS |
|----------|----------|-------|
| Лицензия | Apache 2.0 (бесплатно) | MIT (бесплатно) |
| Инфраструктура | Может работать в памяти или с персистентным хранилищем | В памяти или файловый режим |
| Накладные расходы серверного режима | ~200-500 МБ ОЗУ | ~50-100 МБ ОЗУ (только библиотека) |
| Управляемые облачные варианты | Chroma Cloud (платно) / self-hosted | Только self-hosted |
| Инженерное время (настройка + поддержка) | ~4-8 часов изначально, ~2 часа/мес | ~16-24 часа изначально, ~5 часов/мес |
| **Итоговая стоимость** | **Низкая** (бесплатно, минимальная поддержка) | **Низкая-средняя** (бесплатно, больше поддержки) |

**Вывод**: Обе бесплатны и open-source. ChromaDB имеет меньшие накладные расходы на поддержку.

### **Итоговая рекомендация по векторной БД для QuantumForge**

| Сценарий | Рекомендация |
|----------|--------------|
| **Быстрый MVP / прототипирование** | **ChromaDB** (простейшая настройка, достаточно для начала) |
| **Продакшн с 21 тыс. док. (текущий масштаб)** | **ChromaDB** (хорошо масштабируется до этого уровня) |
| **Продакшн с 1 млн+ док. (будущее масштабирование)** | **FAISS** или рассмотреть управляемые решения (Pinecone, Weaviate) |
| **Команда с ограниченным ML-инженерным ресурсом** | **ChromaDB** |
| **Требование максимальной производительности** | **FAISS** с индексом HNSW/IVF |

## 4. Рекомендуемая конфигурация сервера для RAG-бота

Для развёртывания RAG-бота в QuantumForge Software необходимо подобрать серверную конфигурацию, которая обеспечит баланс между производительностью, стоимостью и возможностью обработки конфиденциальных данных. Ниже приведены расчёты для ключевых компонентов.

### 4.1 Требования к GPU

| Модель | VRAM (минимум) | Рекомендуемый GPU | AWS-инстанс |
|--------|----------------|-------------------|-------------|
| Llama 3 8B (quantized INT8) | ~10 ГБ | NVIDIA A10G / L4 | g5.2xlarge |
| Llama 3 8B (FP16) | ~16 ГБ | NVIDIA A10G / L4 | g5.2xlarge |
| Llama 3 70B (quantized INT4) | ~40-48 ГБ | NVIDIA A100 80GB / 2×A10G | p4d.24xlarge / g5.12xlarge |
| Llama 3 70B (FP16) | ~140 ГБ | 2×A100 80GB | p4d.24xlarge |
| Mixtral 8x7B (quantized INT4) | ~48 ГБ | NVIDIA A100 80GB | p4d.24xlarge |

**Рекомендация для QuantumForge**:
- Для старта достаточно **Llama 3 8B (quantized INT8)** на **AWS g5.2xlarge** (1×A10G, 24 ГБ VRAM)
- При необходимости улучшения качества — переход на **Llama 3 70B (INT4)** на **g5.12xlarge** (4×A10G, 96 ГБ VRAM)

### 4.2 Требования к CPU

| Компонент | Минимум | Рекомендуемое |
|-----------|---------|---------------|
| Процессор | 4 vCPU | 8-16 vCPU |
| Пример | Intel Xeon (g5.xlarge) | Intel Xeon Scalable (g5.2xlarge / g5.4xlarge) |
| Назначение | Обработка запросов, API-шлюз, препроцессинг | + пайплайн индексации, эмбеддинги на CPU (резерв) |

**Рекомендация**: **8 vCPU** — достаточно для обработки API-запросов, препроцессинга документов и оркестрации.

### 4.3 Требования к ОЗУ (RAM)

| Компонент | Потребление |
|-----------|-------------|
| Модель LLM (загрузка в VRAM) | Не использует системную RAM (использует VRAM GPU) |
| ChromaDB (21 тыс. док., 768 dim) | ~200-500 МБ |
| Python-процессы (FastAPI, LangChain) | ~500 МБ-1 ГБ |
| Кэширование + буфер | ~2-4 ГБ |
| **Итого (рекомендуемое)** | **8-16 ГБ** |

**Рекомендация**: **16 ГБ RAM** — комфортный запас для пиковых нагрузок и фоновой индексации.

### 4.4 Требования к хранилищу

| Компонент | Объём |
|-----------|-------|
| Модели (Llama 3 8B + эмбеддинги) | ~10-20 ГБ |
| ChromaDB (21 тыс. док. + метаданные) | ~1-2 ГБ |
| Логи + кэш | ~5-10 ГБ |
| **Итого (минимум)** | **~30-50 ГБ SSD** |
| **Итого (с запасом на рост)** | **~100 ГБ SSD** |

**Рекомендация**: **100 ГБ gp3 EBS** — достаточно на 12+ месяцев роста базы знаний.

### 4.5 Итоговые конфигурации сервера

| Параметр | Минимальная (Llama 3 8B) | Рекомендуемая (Llama 3 70B INT4) |
|----------|--------------------------|----------------------------------|
| **Инстанс AWS** | g5.2xlarge | g5.12xlarge |
| **GPU** | 1×A10G (24 ГБ VRAM) | 4×A10G (96 ГБ VRAM суммарно) |
| **vCPU** | 8 | 48 |
| **RAM** | 32 ГБ | 192 ГБ |
| **Хранилище** | 100 ГБ gp3 EBS | 200 ГБ gp3 EBS |

**Рекомендация для QuantumForge**: Начать с **g5.2xlarge (spot)** для MVP. При необходимости более качественных ответов масштабироваться до **g5.12xlarge**.

### Финальная рекомендация: **Вариант 3 — «Гибридный продакшн»** ⭐

**Аргументация**:

1. **SOC 2 compliance**: QuantumForge готовится к аудиту SOC 2. Вариант 3 обеспечивает полную изоляцию конфиденциальных данных — политики безопасности, данные клиентов и спецификации проектов обрабатываются исключительно внутри AWS.

2. **Баланс качества и стоимости**: Llama 3 70B (INT4) по качеству приближается к GPT-3.5 Turbo, а в комбинации с GPT-4o-mini для общих документов обеспечивает общее качество 8.5/10. При этом стоимость в 3-4 раза ниже полностью локального решения (Вариант 4).

3. **Использование существующей инфраструктуры**: QuantumForge уже использует AWS EKS, что упрощает развёртывание и снижает операционные расходы.

4. **Масштабируемость**: Архитектура готова к росту до 100 тыс.+ документов, что соответствует прогнозируемому росту базы знаний (400 док./мес → ~36 тыс. через 2 года).

5. **Практический путь развёртывания**:
   - **Недели 1-2**: MVP на Варианте 2 (g5.2xlarge + Llama 3 8B) для быстрой демонстрации ценности
   - **Недели 3-4**: Масштабирование до Варианта 3 (g5.12xlarge + Llama 3 70B) для продакшн-качества
